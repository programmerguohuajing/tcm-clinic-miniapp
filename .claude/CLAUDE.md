# CLAUDE.md

## 项目经验总结（tcm-clinic-miniapp）

### 1) 项目定位与当前成果
- 该项目已形成“微信小程序用户端 + 小程序内嵌管理端 + Node/Express 后端 + PC 管理端”的 MVP 骨架，业务闭环覆盖：门店展示、预约下单、健康档案、订单管理、经营看板、内容营销、技师工作台。
- 工程结构采用 `pnpm workspace`，将后端、PC 管理端、共享包集中在同一仓库；移动管理能力已收敛到微信小程序内嵌管理端，不再维护 H5/多端管理端。

### 2) 架构设计经验
- **Monorepo + 共享域层仍有收益**：`packages/admin-shared` 统一承载 PC 管理端 API 定义、状态枚举与格式化逻辑；小程序管理端复用原生 `request` 封装直连 `/api/admin/*`。
- **后端作为统一业务入口**：所有端都走 `/api`，并保持统一响应结构（`{ data }`），前端接入与切换成本低。
- **移动管理能力内嵌到微信小程序**：经营看板、多门店、服务项目、技师、排班、订单、提成、首页配置、内容、会员权限、评价和操作日志集中在 `miniprogram/pages/admin`。
- **多门店能力通过 `store_id` + 公共数据策略落地**：部分查询使用“门店数据 + 通用数据（`store_id is null`）”混合过滤，既支持门店隔离又支持总部复用。

### 3) 业务建模经验
- **预约并发控制必须前置设计**：预约创建在事务中执行，并通过 `select ... for update` 锁定排班，结合容量校验避免超卖。
- **排班模型要支持批量生成**：通过 `(practitioner_id, work_date, start_time)` 唯一约束 + 批量 upsert，能高效覆盖排班场景。
- **管理权限先做“可用最小集”**：当前以 `admin_role` + `can_manage` 实现入口控制，足够支撑 MVP 阶段验证。
- **审计日志对后台场景价值高**：管理端关键写操作统一记录 `admin_audit_logs`，有助于追溯与风控。

### 4) 前后端协作经验
- **MVP 联调要允许降级运行**：小程序端在接口失败时提供 mock/fallback，保证演示与流程验证不中断。
- **统一“演示身份”降低联调门槛**：通过 `x-demo-user-id` 贯穿端到端，快速完成权限、预约、管理功能联调。
- **小程序管理端优先保证移动闭环**：移动侧运营能力应优先在微信小程序内嵌管理端完成，避免再引入 H5/多端管理端维护成本。

### 5) 工程与质量经验
- **输入校验集中化**：后端使用 Zod 在路由层做参数校验，统一错误输出，前端处理更稳定。
- **本地初始化流程完整**：`db:init` + `db:seed` 支撑快速拉起，演示数据覆盖核心业务链路，有利于开发与验收。
- **验证脚本聚焦当前端形态**：根脚本保留 API、PC 管理端和 Playwright E2E 验证；小程序原生管理端需通过微信开发者工具手工验收关键路径。

### 6) 当前阶段的主要不足
- 认证仍是演示模式（`x-demo-user-id`），尚未接入真实微信登录与 JWT 鉴权流程。
- 支付链路未接入（订单仅到状态流转），缺少支付回调与对账闭环。
- 媒体文件（如健康档案图片）仍未接对象存储与访问控制。
- 权限模型仍偏粗粒度，后续需要菜单级/动作级细分授权。

### 7) 后续迭代优先级建议
1. **先补认证与支付闭环**：微信登录 + JWT、JSAPI 支付 + 回调验签 + 订单状态机完善。
2. **再补权限与审计深化**：按角色拆分可见模块和操作权限，审计日志增加检索与导出。
3. **最后做体验与运营增强**：预约改期/取消策略、优惠券规则引擎、消息通知、经营分析报表深化。

### 8) 团队协作约定（建议固化）
- 新增 PC 管理端接口时，优先更新 `packages/admin-shared`；新增小程序管理端能力时，同步检查 `miniprogram/pages/admin` 的模块配置。
- 涉及预约库存/容量变更的逻辑，必须保留事务与锁语义，不可仅靠前端限制。
- 管理端写操作默认接入审计日志；新增后台模块时同步补齐审计字段。
- 所有新增接口保持响应结构和错误语义一致，保证多端可复用性。
