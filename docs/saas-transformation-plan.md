# SAAS 化改造计划：从单业态中医馆到多业态 SaaS 平台

> 文档性质：产品改造路线图（Roadmap / Transformation Plan）
> 配套文档：[PRD-多业态可配置 C 端页面](./prd-multi-industry-cpages.md)
> 现状基线：基于 `AGENTS.md`、`PRODUCT.md`、`DESIGN.md`、`schema.sql`、`home.wxml`、`packages/admin-shared/src/constants.js` 实地核查

---

## 1. 现状结论（Ground Truth）

| 维度 | 现状 | 证据 |
|------|------|------|
| 业务形态 | 单一业态（中医馆 / 按摩理疗） | `PRODUCT.md` 定位、种子数据均为中医场景 |
| 多租户 | **无租户层**。`stores` 无 `tenant_id`，`services/services/practitioners/schedules/appointments` 直接挂在 `store_id` | `backend/database/schema.sql` 第 24-124 行 |
| 业态区分 | 无任何"业态 / 行业类型"字段，业务术语全部硬编码 | `miniprogram/pages/home/home.wxml` 第 13/29/31/77 行硬编码「中医馆 / 选择技师 / 青囊中医馆 / 疗愈体验」 |
| 管理端术语 | 导航标签写死「技师管理 / 技师排班 / 技师工作台 / 提成结算 / 健康档案」 | `packages/admin-shared/src/constants.js` 第 1-14 行 |
| 认证隔离 | 演示模式 `x-demo-user-id`，无真实微信登录、无租户隔离 | `AGENTS.md` 第 6 节「主要不足」 |
| 页面可配置 | **已有雏形**：`homepage_configs` 用 `section_key + title + payload(jsonb)` 做首页区块配置，但挂在 `store_id` 且仅服务首页 | `schema.sql` 第 199-209 行、`catalog.js` 第 38-49 行 |
| 工程结构 | pnpm monorepo：`backend` + `pc-admin` + `packages/admin-shared` + `miniprogram` | `package.json` workspaces |

**核心瓶颈（一句话）**：当前系统是"一个中医馆的代码复印"，业务术语、数据模型、页面结构全部与"按摩 / 中医"强耦合，无法在不改代码的前提下新增一个健身房租户。

## 2. 改造目标（Why）

### 2.1 业务目标
- **一份代码服务多业态**：同一套平台可承载中医馆、健身房、美容院、宠物店等，新增业态从"开发项目"降级为"配置模板"。
- **多租户隔离**：每个商户独立数据、独立品牌（名称 / 主色 / 术语 / 页面结构），平台方统一运维。
- **降低交付成本**：商户入驻从"定制开发"变为"SaaS 开通 + 模板配置 + 微调"，交付周期从月级降到天级。

### 2.2 用户目标
- **商户（租户管理员）**：入驻后选一个业态模板，改品牌名 / 主色 / 首页区块，无需开发即可上线。
- **C 端顾客**：无论进的是中医馆还是健身房，都看到符合该业态心智的清晰页面与术语（技师 ↔ 教练，预约 ↔ 约课）。

## 3. 目标架构（To-Be）

```
┌─────────────────────────────────────────────────────────────┐
│                      SaaS 平台层（Platform）                  │
│   租户管理 · 套餐/能力包（门控菜单与能力）· 开通/停用 · 全局运维 [Phase 3] │
└───────────────┬─────────────────────────────────────────────┘
                │ tenant_id 贯穿所有请求（子域名 / 小程序 appid 解析）
┌───────────────▼─────────────────────────────────────────────┐
│                  业态模板层（Industry Template）               │
│   模板决定：可用模块清单 · 术语映射 · 默认首页区块 · 数据模型差异 │
│   例：中医馆 / 健身房 / 美容院 / 宠物店                       │
└───────────────┬─────────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────────┐
│              C 端页面引擎（Page Engine）  ← 本期 PRD 范围       │
│   按 tenant 的模板 + page_config 动态渲染 section 区块          │
│   术语通过术语字典渲染，杜绝硬编码                              │
└───────────────┬─────────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────────┐
│       管理端（pc-admin + 小程序内嵌）  ← Phase 2 模板化         │
│   按业态模板展示不同模块（技师 ↔ 教练 / 提成 ↔ 课时费）         │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 数据模型演进（关键新增 / 改造）

| 表 | 变更 | 说明 |
|----|------|------|
| `tenants`（新增） | `id, slug, name, industry_type, brand_name, primary_color, status, plan, created_at` | 租户 / 商户主表 |
| `stores` | 新增 `tenant_id` | 门店归属租户 |
| `services / practitioners / schedules / appointments / orders / reviews / articles / activities` | 新增 `tenant_id`（冗余，便于隔离与查询） | 行级租户隔离 |
| `industry_templates`（新增） | `key, name, modules(jsonb), terms(jsonb), default_sections(jsonb)` | 业态模板：模块、术语、默认区块 |
| `homepage_configs` → `tenant_page_configs`（升级） | `tenant_id` 替代 `store_id`；`page_key` 支持多页 | 租户级页面区块配置 |
| `term_dictionaries`（新增或并入模板） | `tenant_id, key, label` | 术语映射（technician→教练） |

**支付能力层（Payment）**：跨 C 端与订单，按"主体类型 + 商品类型"路由「虚拟支付（个人 / 虚拟商品）」或「微信支付（个体户 / 企业 / 到店服务）」，平台不碰资金。详见 [支付 PRD](./prd-payment-multi-subject.md)。

## 4. 分阶段路线图（Roadmap）

### Phase 0 — 多租户地基（前置，非本期 PRD）
- **目标**：打通"一个平台、多个独立租户"的数据与请求隔离。
- **范围**：
  - 新增 `tenants` 表；`stores/*` 全表加 `tenant_id`。
  - 请求上下文中间件：从子域名 / 小程序 appid 解析 `tenant_id`，所有查询自动带 `tenant_id` 过滤（复用现有 `storeFilter` 模式升级为 `tenantFilter`）。
  - 认证升级：演示模式 → 真实微信登录 + 租户隔离（JWT 携带 `tenant_id` + `user_id`）。
- **验收**：同一套代码，两个租户数据完全隔离、互不可见。
- **依赖**：需先决策"租户识别方式"（子域名 vs 小程序 appid 多环境）。

### Phase 1 — 业态模板 + C 端页面引擎（**本期 PRD 核心**）
- **目标**：C 端页面按业态模板 + 配置动态渲染，术语不再硬编码，新增"健身房"租户零代码。
- **范围**：见配套 PRD。`industry_templates`、`tenant_page_configs`、术语字典、小程序端渲染引擎改造。
- **验收**：后台选"健身房"模板并改品牌名/主色/首页区块，C 端立即呈现"教练 / 约课 / 会员卡"心智的页面。

### Phase 1.5 — 多主体支付能力（商户收款，可与 Phase 1 并行）
- **目标**：接入两套支付通道——个人主体虚拟支付（仅虚拟商品）+ 个体工商户 / 企业微信支付（到店服务），按规则自动路由，订单状态机补齐回调与对账。详见 [支付 PRD](./prd-payment-multi-subject.md)。
- **范围**：`subject_type` / `goods_type` 模型、支付路由、虚拟支付三接口（下单 / 发货推送 / 查单兜底）、微信支付 JSAPI + 通知、虚拟商品发货。
- **验收**：个人主体卖线上课程收款成功；个体户预约到店服务微信支付成功；个人主体下到店服务订单被拦截提示升级。
- **依赖**：Phase 0 租户模型（`subject_type`）；可与 Phase 1 并行。

### Phase 2 — 管理端模板化
- **目标**：pc-admin 与小程序内嵌管理端按业态展示模块，导航/表单/标签用语随模板变化。
- **范围**：`admin-shared/constants.js` 的 `navItems` 改为模板驱动；表单字段按业态显隐（如健身房显示"课时"，中医馆显示"疗程"）。
- **验收**：中医馆租户看不到"团课管理"，健身房租户看不到"健康档案"。

### Phase 3 — 套餐与能力包（Plan-based Entitlement，P2，晚于 PRD）
- **目标**：用"套餐 / 能力包"控制租户可见的菜单与能力；**不做计费、不做用量计量**（用户已明确不需要）。
- **范围**：套餐定义（基础 / 专业 / 旗舰等）决定可用 nav 菜单项与功能模块（如专业版开放"多门店 / 营销 / 数据看板"，基础版仅核心预约）；门店数 / 席位等上限作为能力约束而非计费项。
- **说明**：仅做能力门控，不接入支付 / 账单 / 用量统计；架构上需在 Platform 层预留 `plan → menu/capability` 映射。本阶段依赖 Phase 0-2 稳定，**不进入本期 PRD 范围**。

## 5. 关键架构决策（ADR）

**ADR-1：行级 `tenant_id` 隔离 + 请求中间件注入**
所有业务表冗余 `tenant_id`，由中间件统一注入过滤。理由：比 schema-per-tenant 更易运维，比纯 store 层级更适合"平台方统一看板"。

**ADR-2：业态模板"预置 + 受控配置"，而非完全自由画布**
C 端页面 = 模板预置的 section 组合 + 商户在限定范围内的开关/排序/文案微调。理由：避免"自由拖拽"带来每个租户都长不一样的维护灾难，也保证各业态体验一致性。完全自定义区块列为 P2。

**ADR-3：术语抽象层（Term Dictionary）**
所有面向用户的业务名词（技师、预约、健康档案…）走术语字典渲染，代码零硬编码中文业务词。理由：这是"支持多业态"的最低成本支点，home.wxml 的硬编码正是本期要消除的债。

**ADR-4：页面引擎复用 `homepage_configs` 模式并升级**
将 `section_key + payload(jsonb) + sort_order` 从 store 级升级为 tenant 级、多 page 支持。理由：已有可运行雏形，风险最低。

**ADR-5：套餐 = 能力包门控，不做【平台向租户】计费 / 用量**
套餐仅定义"可用菜单 + 可用能力"集合，与 tenant 关联；平台据此在管理端与 C 端隐藏无权限的菜单 / 模块。明确不接入平台向租户的计费、账单、用量计量；但与本期新增的"租户向顾客收款"支付能力性质不同（见 ADR-6）。理由：用户确认 SaaS 价值在于"不同套餐对应不同菜单和能力"，而非平台按量收费。

**ADR-6：支付按"主体类型 + 商品类型"路由，虚拟支付仅限虚拟商品**
支付通道由系统按 `(subject_type, goods_type)` 自动选择：个人主体 + 虚拟商品 → 虚拟支付；个体工商户 / 企业 → 微信支付；个人主体 + 到店服务 → 拦截并引导升级主体。理由：微信虚拟支付官方仅面向虚拟商品、类目限"工具"、月限 10 万；到店服务（预约 / 团课）属实物服务，个人主体用虚拟支付售卖违规。平台不碰资金、不抽成。

## 8. 需老板 / 利益方对齐的决策（Open Questions）

1. **租户识别方式**：子域名（`gym.a.com`）、还是微信小程序多 appid / 多环境？—— 影响 Phase 0 实现。
2. **首期支持哪些业态**：仅"中医馆 + 健身房"，还是顺带"美容院/宠物店"？—— 影响模板设计广度。
3. **套餐 / 能力包范围**：已确认不做计费与用量；套餐仅做"菜单 + 能力"门控。需确认首期套餐档位（如基础 / 专业 / 旗舰）及各档对应的菜单 / 能力清单。
4. **"团课 / 会员卡次卡"是否进 Phase 1**：还是先只做"服务预约"通用模型，团课留 P1？
5. **品牌视觉**：每个租户是否允许自定义主色（已有 DESIGN.md 橘红体系），还是平台统一视觉 + 仅换 logo/名称？
6. **各业态类目是否命中虚拟支付"工具"类目**：不命中则个人主体无法变现，需确认（中医馆 / 健身房类目归属）。
7. **个人主体月限 10 万是否满足首期**：超限引导策略（提示升级主体 / 拆分）。
8. **"预约定金 / 诚意金"是否可被个人主体合规支付**：需法务 / 平台确认边界，避免到店服务借定金绕过。
