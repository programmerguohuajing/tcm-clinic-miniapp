# PRD：多主体支付能力（个人虚拟支付 + 个体工商户微信支付）

> 文档性质：产品需求规格（Feature Spec / PRD）
> 配套文档：[SAAS 化改造计划](./saas-transformation-plan.md) · [多业态 C 端页面 PRD](./prd-multi-industry-cpages.md)
> 范围：商户向 C 端顾客收款的支付通道能力（**非平台向租户计费**）
> 事实基线：微信官方《虚拟支付：个人》文档（2026-08 上线）、AGENTS.md「支付链路未接入」

---

## 0. 范围澄清（避免与"不做计费"混淆）

- **平台计费（SaaS 向租户收费）**：不做（用户已确认）。
- **商户收款（租户向 C 端顾客收费）**：本期要做。即本 PRD。
- 二者性质不同：平台不碰资金、不抽成；资金由微信侧直结算到商户/个人（虚拟支付 T+3 提现、微信支付 T+1 落商户号）。

---

## 1. 问题陈述（Problem Statement）

1. 当前 C 端订单"仅到状态流转"，**支付链路完全未接入**（AGENTS.md 第 6 节），商户无法收款。
2. 微信已向**个人主体小程序**开放虚拟支付，但仅限**虚拟商品**（会员/课程/内容/次数），且类目限"工具"、月限 10 万。
3. 到店服务（中医理疗预约、健身房团课）属于实物/服务类，个人主体**不能**用虚拟支付售卖，必须走**微信支付**（个体工商户/企业 + 商户号）。
4. 系统当前无任何支付抽象，无法按"主体类型 + 商品类型"路由通道，也无法处理两套回调/对账语义。

**不解决的代价**：个人开发者商户无法变现；个体户商户无法收预约款；若错误用虚拟支付卖到店服务，存在违规下架风险。

---

## 2. 目标（Goals）

| # | 目标 | 类型 | 成功标准 |
|---|------|------|---------|
| G1 | 平台支持两套支付通道并按规则自动路由 | 技术/平台 | 下单时按 (subject_type, goods_type) 正确选通道 |
| G2 | 个人主体商户可合规售卖虚拟商品并收款 | 用户 | 线上课程/会员内容通过虚拟支付完成收款 |
| G3 | 个体户/企业商户可售卖到店服务并收款 | 用户 | 预约/团课走微信支付 JSAPI 完成收款 |
| G4 | 订单状态机补齐支付回调与对账（发货/退款） | 技术 | 支付状态与通道侧一致（查单兜底） |

---

## 3. 非目标（Non-Goals）

1. **不做平台向租户计费 / 抽成 / 账单 / 用量计量**（与确认一致）。
2. **虚拟支付不用于到店实物 / 服务类商品**：个人主体商户的"到店预约"类商品在支付环节被拦截并引导升级主体，不做"打擦边球"兼容。
3. **不接入除微信系以外的第三方支付**（首期仅虚拟支付 + 微信支付）。
4. **不建平台统一资金池 / 分账中台**（首期资金直连商户/个人；如需平台分润留 P2）。
5. **不做 Apple IAP 之外的 iOS 特殊通道**（iOS 走虚拟支付内置 Apple IAP）。

## 4. 用户故事（User Stories）

**个人主体商户**
- 作为个人主体商户，我希望上架"线上课程 / 会员内容"并用虚拟支付收款，以便不注册公司也能变现。
- 作为个人主体商户，我尝试上架"到店理疗预约"并收款时，系统提示"该商品需个体工商户主体 + 微信支付"，并引导我升级主体，以便合规。
- 边界：我的月收款接近 10 万限额时，系统给出预警，避免超额订单支付失败。

**个体工商户 / 企业商户**
- 作为个体户商户，我希望顾客预约到店服务时走微信支付，以便正常经营、可对账。
- 作为个体户商户，我也可以选择用虚拟支付售卖线上内容（双通道并存）。

**C 端顾客**
- 作为顾客（个人主体小程序），我买线上课程用虚拟支付：下单 → 拉起支付 → 支付成功 → 权益发放（会员/次数/内容解锁）顺畅；退款有兜底。
- 作为顾客（个体户小程序），我预约到店服务用微信支付，支付结果实时回写订单。
- 边界：支付成功但推送丢失时，系统通过查单兜底补发权益，顾客不白付。

**平台运营**
- 作为平台运营，我希望支付通道按规则路由，且订单支付状态与微信 / 虚拟支付侧一致，以便对账无误。

## 5. 需求（Requirements）

### P0 — Must Have

**R1 主体与商品类型模型**
- `tenants` 新增 `subject_type`（personal / individual_business / enterprise）。
- 商品（services / 课程 / 会员卡）新增 `goods_type`（virtual / real_service）。
- 验收：新建租户需选择主体类型；上架商品需选择商品类型。

**R2 支付路由规则**
- 下单时按 `(subject_type, goods_type)` 路由：
  - personal + virtual → **虚拟支付**
  - individual_business / enterprise + 任意 → **微信支付**
  - personal + real_service → **拦截**，返回"需升级为个体工商户"引导
- 验收：个人主体下单到店服务被拦截并提示升级；其余按表路由。

**R3 虚拟支付接入（个人 / 虚拟商品）**
- 小程序端：`wx.requestVirtualPayment`（需 AppID / OfferID / 现网 AppKey，道具已在 MP 后台创建发布）。
- 服务端三接口：`POST /pay/order`（下单返回 payData）、`POST /pay/notify`（接收 `xpay_goods_deliver_notify` 验签发货）、`POST /pay/query`（调用 `query_order` 查单兜底）。
- 以 `wx_order_id` 做幂等去重；`outTradeNo` 每次唯一（8–32 位）。
- 验收：小额真单跑通 支付→推送→发货→账单一致。

**R4 微信支付接入（个体户 / 企业 / 到店服务）**
- JSAPI 支付（`wx.requestPayment`）+ 支付结果通知 + 退款通知。
- 订单状态机：待支付 → 已支付 → 已发货/已完成；退款 → 已退款。
- 验收：预约订单微信支付成功，订单状态实时更新。

**R5 订单状态机补全与对账**
- 统一支付状态码（待支付/已支付/已退款/退款中），两通道共用。
- 以通道侧单号为准；虚拟支付以发货推送为主、查单兜底；微信支付以结果通知为主。
- 验收：模拟推送丢失，查单兜底补发，订单终态正确。

**R6 虚拟商品发货**
- 支付成功后发放权益（会员等级/次数/内容解锁），支持推送 + 查单兜底双路径。
- 验收：虚拟商品支付后权益准确发放，重复推送不重复发放。

### P1 — Should Have

**R7 iOS 苹果 IAP 支付**：虚拟支付 iOS 通道（需配置小程序简称 + 开通 Apple IAP，定价/现金流单独测算，佣金 12%、结算 45–60 天）。
**R8 退款闭环**：虚拟支付 Android 主动退款（`refund_order`）/ iOS 走 Apple；微信支付退款；退款推送 `xpay_refund_notify` 处理，180 天内退手续费规则。
**R9 商户交易视图**：后台查看交易订单、账单、提现状态（虚拟支付余额/账单；微信支付交易记录）。

### P2 — Future

**R10 代币 / 会员订阅订单**：虚拟支付支持的代币、订阅类型。
**R11 支付能力作为套餐门控项**：`plan → capability` 映射中"支付"可设为某套餐专属（与 Phase 3 协同）。
**R12 平台分润 / 多商户分账**（如未来平台抽成，本期不做）。

## 8. 时间考虑（Timeline）

- **硬依赖**：Phase 0 租户模型（`subject_type` 字段）先于 R1。
- **可并行**：Phase 1.5 支付能力可与 Phase 1（C 端页面）并行启动，因订单/服务模型已存在。
- **建议拆分**：
  - **1.5a 模型与路由**：`subject_type` / `goods_type` + 支付路由（R1/R2）。
  - **1.5b 虚拟支付**：三接口 + 小程序端 + 发货（R3/R6）。
  - **1.5c 微信支付**：JSAPI + 状态机 + 通知（R4/R5）。
  - **1.5d 收尾**：退款 + 商户交易视图（R7–R9 视资源）。
